## 1. Контекст и мотивация

Сейчас автоматическая коррекция держится на точном совпадении со словарём
(`WordValidator.validate` → `DictionaryLoader.containsExact`): слово считается набранным
в неправильной раскладке, только если оно **не** найдено в словаре текущего языка, а его
конвертация **найдена** в словаре другого.

### Выявленные проблемы

**П1. Покрытие `ru_RU` и `en_US` — почти только леммы.**

| Словарь | Строк | Содержимое |
|---|---|---|
| `uk_UA.txt` | 2 958 567 | полные словоформы (`зробила`, `програмістами`, `комп'ютерах` — есть) |
| `ru_RU.txt` | 146 229 | почти только начальные формы (`делает`, `работает`, `говорит`, `дома`, `работы`, `сделала` — **нет**) |
| `en_US.txt` | 48 241 | почти только начальные формы (`worked`, `working`, `played`, `cats`, `houses`, `commits`, `deployed` — **нет**) |

Следствие: `hf,jnftn` («работает») и `сфеы` («cats») не исправляются никогда. Морфологии
и стемминга в `containsExact` нет.

**П2. Принципиальная неполнота любого словаря.** Неологизмы, сленг, имена, термины,
бренды, опечатки (`ghbdtnn`) — не распознаются, даже если бы словари были полными.

**П3. Вес.** Исходники словарей — ~70 МБ в репозитории (`uk_UA.txt` — 67 МБ), отдельный
компилятор (`scripts/compile_dictionary.swift`), бинарный формат `SFDICT2`, bloom-фильтр,
mmap, логика поиска бандла в двух раскладках (`build-app.sh` ↔ `findDictionaryURL`),
`AutomaticDictionaryReadiness`. Всё это — поддерживаемый код ради одной булевой проверки.

**П4. Короткие слова и неоднозначность** уже сейчас закрываются набором эвристик поверх
словаря (`lowConfidence*`, `shortWordSuppression*`, аббревиатуры) — словарь сам по себе
эту задачу не решает.

### Рассмотренные альтернативы

| Подход | Без словарей? | Вердикт |
|---|---|---|
| Hunspell (`.dic` + `.aff`) | нет — это словарь с морфологией | ❌ не решает цель |
| Полные списки словоформ (OpenCorpora, SCOWL) | нет | ❌ решает только П1 |
| `NSSpellChecker` | формально да, фактически системный словарь | ❌ П2 остаётся; поведение зависит от версии macOS и выученных пользователем слов; наличие украинского и задержку/потокобезопасность нужно отдельно проверять; тесты становятся ОС-зависимыми |
| **Символьная n-граммная модель** | **да** | ✅ выбран |
| ML-классификатор (Core ML) | да | ❌ избыточно для 3 языков; n-граммы дают то же проще и прозрачнее |

## 2. Цели и не-цели

### Цели
1. **Удалить словари полностью**: `Sources/Dictionary/Resources/*.txt`, `overrides/`,
   `compile_dictionary.swift`, `SFDICT2`, `BloomFilter`, `MappedDictionary`, `DictionaryLoader`,
   `WordValidator`, `DamerauLevenshtein`, `SuggestionEngine` (кроме таблицы коротких слов).
2. **Решение о неправильной раскладке — по символьной n-граммной модели** языков en / ru / uk.
3. **Личное обучение**: отмена автокоррекции → слово больше не исправляется; ручная
   конвертация хоткеем → слово исправляется автоматически в следующий раз.
4. **Качество не хуже текущего** на существующих тестах `TestRunner` и строго лучше на
   словоформах и незнакомых словах (см. §8).
5. **Размер модели ≤ 1 МБ** на все языки, детекция одного слова p99 ≤ 50 мкс.
6. Сохранить все инварианты `plan/003` (staleness-guards в `prepareCorrection` /
   `CorrectionPlan.isEligible`, физический ввод не задерживается).

### Не-цели (эта фаза)
1. **Коррекция посреди слова** (до пробела). Модель это позволяет, но это меняет
   конвейер `InputStateMachine` — отдельный план после стабилизации.
2. Новые языки/раскладки сверх `Layout.english/.ukrainian/.russian`.
3. Контекстная модель на уровне слов (word n-grams) — только символы внутри слова плюс
   существующий `recentOutcomes`.
4. Изменение ручной коррекции хоткеем (`forceConversion`) — она уже не зависит от словаря
   и остаётся как есть.

## 3. Результаты прототипа

Скрипт: `plan/benchmarks/ngram_prototype.py` (запуск из корня репо,
`python3 plan/benchmarks/ngram_prototype.py [n]`).

**Методика.** Триграммная модель (add-k сглаживание, k=0.1, маркеры начала/конца слова),
обученная на текущих словарях; 4000 отложенных слов на язык. Для каждого слова:
(а) оно набрано в чужой раскладке — должно сработать; (б) набрано правильно — не должно.
Решение: `margin = logP_target(converted) − logP_source(typed) > T`.

**n=3, T=5:**

| Длина | Ловит неправильную раскладку | Ложные срабатывания |
|---|---|---|
| 6+ букв | 99.62–99.95% | 0% |
| 4–5 букв | 84–97% | 0–1.2% |
| 2–3 буквы | 14–72% | 0–4% |

**Точечные примеры (margin):** `ghbdtn`→привет 18.8 · `hf,jnftn`→работает 19.6 (словарь
не ловит) · `сщььше`→commit 19.0 · `лгиуктуеуы`→kubernetes 24.8 · `yf`→на 12.8 ·
`ns`→ты 0.2 (на грани) · `пше`→git 3.4 · `git`→пше −3.4 · `json`→оыщт −9.6.

**Выбор ru vs uk** для латиницы при обеих установленных кириллических раскладках: в
~60% случаев конвертации совпадают; из остальных модель выбирает правильно в ~97%.

**Размер:** 8–14 тыс. уникальных триграмм на язык.

**n=4 без backoff** на тех же данных хуже по полноте на 4–5 буквах (78–95%) из-за
разреженности — 4-граммы имеют смысл только с интерполяцией/backoff (решается в Фазе 1).

**Ограничения прототипа** (почему цифры — ориентир, а не обещание):
- обучение и проверка на списках слов без частот, а не на живом тексте;
- `ru_RU`/`en_US` — леммы, т.е. модели недообучены на окончаниях;
- в реальном тексте доминируют частые короткие слова — самая слабая зона модели.

```

                                                                  │
                        ── рантайм ──                             │
  InputEngine.runDetection                                        │
        │                                                         │
        ▼                                                         ▼
  LayoutDetector.checkBuffer ──► LayoutScorer ──► CharNgramModel (mmap)   TestRunner: eval suite
        │        ▲                    ▲
        │        │                    └── ShortWordTable (встроенная)

            forceConversion хоткеем ──► PersonalLexicon.recordAccepted
```

### 4.1 `CharNgramModel` (новый модуль `LanguageModel`, заменяет `Dictionary`)

- **n = 3** в первой итерации (решение). Сглаживание — простое add-k/interpolated, как в
  прототипе. 4-граммы с backoff — отдельный эксперимент **после** Фазы 2, только если
  eval-набор покажет конкретные пробелы, которые триграммы не закрывают. Формат файла хранит
  `n` в заголовке, чтобы переход не требовал нового формата.
- Алфавит модели: буквы своего скрипта + апостроф (`'`, `’` нормализуется) + маркеры
  `^`/`$`. Регистр приводится к нижнему.
- Хранение: открытая хеш-таблица `hash(n-грамма) → log-prob`, квантованный в `Int8`
  (шаг ~0.1 nat) или `Float16`; fallback-значение для отсутствующих n-грамм — из
  сглаживания, хранится в заголовке.
- Формат файла `SFNGRAM1`: заголовок (magic, версия, язык, n, размер таблицы,
  seed хеша, unseen-logprob, контрольная сумма) + таблица. Загрузка через mmap, как у
  текущих `.bin`.
- Файлы моделей **коммитятся** в репозиторий (маленькие), чтобы сборка и CI не зависели от
  сети и корпусов. Пересборка — вручную скриптом.
- Упаковка: SwiftPM-ресурс модуля `LanguageModel`. Логику поиска бандла
  (`Contents/Resources` и плоский вариант) перенести из `DictionaryLoader.findDictionaryURL`
  **без изменений** и синхронно поправить `build-app.sh`.

### 4.2 `LayoutScorer`

```swift
struct LayoutScore {
    let target: Layout
    let converted: String
    let margin: Double      // logP_target(converted) − logP_source(typed)
}

func score(word: String, source: Layout, alternatives: [(Layout, String)]) -> LayoutScore?
```

- Кандидаты — как сейчас: `LayoutMapper.convertToAlternatives` + вариант `legacy`/`standard`
  для украинского; отбрасываются кандидаты с «фальшивым» префиксом из пунктуации
  (существующая проверка `tokenParts.prefix.count > originalParts.prefix.count`).
- Из кандидатов берётся лучший по `margin`; при двух кириллических целях (ru и uk)
  сравниваются их `logP` между собой.
- Нормализация: margin суммарный (длины одинаковы), но порог зависит от длины слова.

### 4.3 Правило решения

Порядок проверок в `LayoutDetector.checkBuffer` (остальная логика — буфер, границы,
`applyCase`, слияние отложенных коротких слов — сохраняется):

1. **Фильтры пропуска** (переносятся из `WordValidator.shouldSkip`): числа, URL, e-mail,
   camelCase, смешанные скрипты, английские аббревиатуры в верхнем регистре.
2. **`PersonalLexicon`**: для пары (слово, раскладка набора) правило `.neverCorrect` → не
   трогать; `.alwaysCorrect(to:)` → исправить сразу в указанную раскладку
   (`shouldSwitchLayout = true`). Каждое срабатывание обновляет `matchCount`/`lastMatchedAt`.
3. **Короткие слова (≤ 3 буквы)** → `ShortWordTable` (§4.4); модель используется только
   как дополнительный сигнал при наличии подтверждения контекстом.
4. **Модель**: `margin > threshold(length) + sensitivityOffset`.
   Пороги **не выбираются заранее** — их определяет подбор на eval-наборе в Фазе 2 (§4.6).
   Порог задаётся отдельно для корзин длины 4, 5, 6, 7+ (у коротких слов меньше
   n-грамм → нужна большая уверенность). Для 4–5 букв дополнительно остаётся существующая
   схема low-confidence подтверждения. Значения прототипа (T≈5 для 6+, T≈8 для 4–5) — только
   стартовая точка перебора.

5. Если сработало — `DetectionResult` как сейчас. `recentOutcomes` и
   `hasStrongCurrentContext` продолжают работать: «валидно в текущем языке» теперь
   означает `margin < −T` (т.е. исходное слово явно правдоподобнее конвертации).

### 4.4 `ShortWordTable`

Встроенная (в коде) таблица ~150–250 самых частых слов длиной 1–3 буквы на язык,
отобранных по частоте из тех же корпусов (генерируется `ModelTrainer` в
`ShortWordTable+Generated.swift`). Это не словарь в смысле П1–П3: фиксированный
небольшой набор служебных слов, а не проверка «существует ли слово».
Заменяет `SuggestionEngine.shortWords`. Сохраняется существующая логика: для слов ≤ 3
букв без явного контекста — требуется подтверждение (`lowConfidenceConfirmations`).

### 4.5 `PersonalLexicon` (обучение на действиях пользователя)

- **Модель записи**:
  ```swift
  struct LexiconEntry: Codable, Identifiable {
      let id: UUID
      var word: String              // нижний регистр, как набрано
      var sourceLayout: Layout      // в какой раскладке было набрано
      var rule: Rule                // .neverCorrect | .alwaysCorrect(to: Layout)
      var origin: Origin            // .learnedFromRevert | .learnedFromHotkey | .manual
      var createdAt: Date
      var lastMatchedAt: Date?
      var matchCount: Int
  }
  ```
- **Хранение**: `PreferencesManager`, ключ `SwitchFix_personalLexicon` (JSON-массив
  записей, открытым текстом — решение §10). Лимит 5000 записей; при переполнении
  вытесняются самые давно не срабатывавшие **автоматически выученные** записи — добавленные
  вручную не вытесняются никогда. Потокобезопасный доступ (`OSAllocatedUnfairLock`),
  снимок-словарь `[(word, sourceLayout): rule]` читается на detection-очереди без обращения
  к `UserDefaults` на горячем пути. Изменения публикуются `.personalLexiconDidChange`.
- **`recordRejected(word, sourceLayout)`**: вызывается, когда `TextCorrector.undo` вернул
  `true` (хоткей отмены после автокоррекции) → запись `.neverCorrect`, origin
  `.learnedFromRevert`. Ключ — исходное слово в нижнем регистре, как оно было набрано.
  Существующая запись для той же пары перезаписывается.
- **`recordAccepted(word, sourceLayout)`**: вызывается при успешной ручной коррекции
  хоткеем (`forceConversion`), если автоматическая детекция это слово **не** исправила →
  запись `.alwaysCorrect(to: target)`, origin `.learnedFromHotkey`. Перезаписывает
  существующую запись для той же пары. Записи с origin `.manual` автоматически **не**
  перезаписываются — ручное решение пользователя приоритетнее.
- Нативный Cmd+Z (`.nativeUndo`) сейчас лишь сбрасывает undo-состояние; **не** считать его
  отказом в этой фазе — нельзя надёжно понять, что именно отменило приложение.
- **Приватность**: записи только из не-secure полей (гарантируется существующими
  guards); слова ≤ 32 символов; в логах изменений лексикона — только счётчики, без самих слов.
- **UI — полноценный CRUD**, отдельная вкладка настроек «Слова» (рядом с «Приложения»,
  тот же паттерн `NSHostingController` в `SettingsWindowController`):
  - **Список** (SwiftUI `Table`): слово · раскладка набора · правило (`Не исправлять` /
    `Исправлять → EN/UK/RU`) · источник (`Отмена` / `Хоткей` / `Вручную`) · срабатываний ·
    последнее срабатывание. Сортировка по колонкам, поиск по слову, фильтр по правилу.
  - **Создание**: кнопка `+` → форма: слово, раскладка набора, правило, целевая раскладка.
    Валидация: не пустое, ≤ 32 символов, скрипт слова совпадает с раскладкой набора,
    дубликат (слово + раскладка) → предложить редактировать существующее.
  - **Редактирование**: двойной клик / кнопка — правка любого поля в той же форме.
  - **Удаление**: `−`, клавиша Delete, множественный выбор.
  - «Сбросить выученные автоматически» (оставляет ручные) и «Удалить всё» — с подтверждением.
  - Все строки через `L10n.tr` с русскими переводами.

### 4.6 Подбор порогов и чувствительность

Баланс «ловит больше ↔ реже ошибается» находится **данными**, а не угадывается:

1. **Перебор порогов** (`swift run -c release TestRunner --threshold-sweep`): для каждой
   корзины длины прогоняет пороги с шагом 0.5 по eval-набору и печатает таблицу
   recall / FP. Результат сохраняется в `plan/benchmarks/thresholds_005.md` при каждом
   изменении модели.
2. **Правило выбора значения по умолчанию**: для каждой корзины — минимальный порог, при
   котором FP ≤ цели из §8 (0.1% для ≥ 4 букв). Это даёт максимально возможную полноту
   без превышения допустимого уровня ошибок.
3. **Ползунок «Чувствительность»** во вкладке «Коррекция»: 5 положений
   (`Осторожно` … `Смело`), каждое — сдвиг `sensitivityOffset` ко всем порогам
   (например, −4, −2, 0, +2, +4 после калибровки). Среднее положение = значения из п.2.
   Для каждого положения в `thresholds_005.md` записаны ожидаемые recall/FP, поэтому шаг
   ползунка откалиброван, а не произволен. Хранение: `SwitchFix_detectionSensitivity`.
4. **Калибровка по реальному использованию**: в лог `detector` добавить `margin`, порог и
   длину слова для каждого решения (сами слова — только на уровне `debug`, как сейчас).
   Это позволит в Фазе 4 проверить пороги на собственных логах, а не только на eval.
5. Пороги хранятся в одном месте (`DetectionThresholds` в `Core`) и покрыты тестом,
   который сверяет их с последним прогоном перебора — чтобы обновление модели без
   перекалибровки ломало CI, а не пользователей.

## 5. Корпуса и обучение модели

- **Источники** (проверить лицензии перед использованием): Leipzig Corpora Collection
  (новости/веб, en/ru/uk), OpenSubtitles через OPUS (разговорная речь — ближе к переписке),
  Wikipedia dumps. Для английского дополнительно — технический текст (README/документация),
  чтобы `commit`, `deploy`, `kubernetes` были «английскими».
- **Смесь по жанрам**: разговорный ≥ 50% — пользователи пишут в мессенджерах чаще, чем
  статьи.
- **Токенизация**: слова одного скрипта, нижний регистр, `’`→`'`, отбросить токены с
  цифрами/смешанным скриптом; обучать с учётом **частот** (не список уникальных слов).
- **Обучение — на Swift, отдельный executable-таргет `ModelTrainer`** (решение §10):
  `swift run -c release ModelTrainer --corpus <dir> --out Sources/LanguageModel/Resources`.
  Главный аргумент — **надёжность**: тренер и приложение используют **один и тот же код**
  из модуля `LanguageModel` — нормализацию текста, разбиение на n-граммы, хеш и запись
  формата `SFNGRAM1`. Расхождение «Python считает так, Swift читает иначе» исключено
  конструктивно, и это проверяется тестом (обучить на крошечном корпусе → прочитать
  рантайм-загрузчиком → совпадение log-prob). Скорость тоже в пользу Swift: release-сборка
  проходит сотни МБ текста за минуты. Python-прототип остаётся только как исторический
  референс в `plan/benchmarks/`.
- **Загрузка корпусов**: `scripts/fetch-corpora.sh` — `curl` фиксированных версий с
  проверкой `sha256`, распаковка в `.build/corpora/` (в `.gitignore`). Сами корпуса в
  репозиторий **не** коммитятся.
- **Выход тренера**: `{en,ru,uk}.sfng` + сгенерированный `ShortWordTable+Generated.swift`

## 7. Этапы реализации

### Фаза 0: Eval-набор и baseline ⏱ ~1 ч
- Собрать `Tests/LayoutEval/{en,ru,uk}.txt` из реальных фраз (не из словарей):
  ~5000 слов на язык с частотным распределением живого текста — предложения из тестовых
  частей UD-трибанков (CC BY-SA 4.0, см. `Tests/LayoutEval/README.md`); плюс
  `edge_cases.tsv` — «опасные» строки (идентификаторы кода, аббревиатуры, сленг, имена,
  транслит) и техтермины/словоформы в неправильной раскладке.
- UD-трибанки **не** используются для обучения модели — eval остаётся отложенным.
- Добавить в `TestRunner` eval-suite, прогоняемый против **текущего** словарного
  детектора → baseline recall/FP по длинам в `plan/benchmarks/baseline_005.md`.

### Фаза 1: Триграммная модель и тренер ⏱ ~4 ч
- `TextNormalization`, `SFNGRAM1`, `CharNgramModel`, `ModelLoader` в `LanguageModel`.
- Таргет `ModelTrainer`, `scripts/fetch-corpora.sh`, обучение n = 3 на корпусах.
- Тесты: битый заголовок / несовпадение версии / отсутствующий файл → язык недоступен;
  round-trip тренер → рантайм.
- **Критерий выхода**: размер ≤ 1 МБ суммарно; на eval-наборе recall/FP не хуже прототипа.

### Фаза 2: Скорер, детектор за флагом, подбор порогов ⏱ ~4 ч
- `LayoutScorer`, `ShortWordTable`, `DetectionThresholds`, новое правило в `LayoutDetector`.
- Скрытый флаг `SwitchFix_detectionEngine = dictionary | ngram` (по умолчанию
  `dictionary`), чтобы сравнивать в реальной работе.
- `TestRunner --threshold-sweep` → `plan/benchmarks/thresholds_005.md`; пороги по
  умолчанию и шаги ползунка выбираются по правилу §4.6.
- Логирование `margin`/порога для калибровки на реальном использовании.
- **Критерий выхода**: eval-suite зелёный по целям §8; все существующие тесты
  `TestRunner`/`InputPipelineTestRunner` проходят в режиме `ngram` (тесты, завязанные на
  конкретные словарные слова, переписываются с сохранением смысла).
- **Точка решения**: если цели §8 не достигнуты на триграммах — эксперимент с 4-граммами
  + backoff, прежде чем двигаться дальше.

### Фаза 3: `PersonalLexicon`, вкладка «Слова», ползунок ⏱ ~5 ч
- Хранилище и CRUD-API, хуки в `InputEngine`.
- Вкладка «Слова» (таблица, поиск, фильтр, создание/редактирование/удаление, сброс).
- Ползунок «Чувствительность» во вкладке «Коррекция».
- Все строки — `L10n.tr` + русские переводы.
- Тесты в `InputPipelineTestRunner` через инъекцию: автокоррекция → revert → то же слово
  больше не исправляется; ручная конвертация → то же слово исправляется автоматически;
  конфликт автоматических правил — побеждает последнее действие, ручная запись не перезаписывается автоматически; ручная запись не вытесняется лимитом;
  сдвиг чувствительности меняет решение на пограничном слове.

### Фаза 4: Переключение и удаление словарей ⏱ ~2 ч
- Флаг по умолчанию → `ngram`, пожить с этим (личное использование) ≥ 1 неделю;
  по логам `margin` и по содержимому вкладки «Слова» (что приходилось отменять) —
  при необходимости перекалибровать пороги и повторить перебор.
- Удалить `Sources/Dictionary`, `compile_dictionary.swift`, флаг, словарные тесты.
- Обновить `build-app.sh`, CI, `CLAUDE.md`, `README.md`.
- Проверить `./scripts/build-app.sh` → `.app` запускается, коррекция работает, размер DMG
  уменьшился.

## 8. Метрики и критерии приёмки

На eval-наборе Фазы 0 (реальный текст, не словари):

| Метрика | Цель |
|---|---|
| Ложные срабатывания, слова ≥ 4 букв | ≤ 0.1% |
| Ложные срабатывания, слова ≤ 3 букв | ≤ 0.5% |
| Полнота, слова ≥ 6 букв | ≥ 98% |
| Полнота, слова 4–5 букв | ≥ 90% |
| Полнота на словоформах ru/en (П1) | ≥ 95% (сейчас ≈ 0% для отсутствующих форм) |
| Выбор ru vs uk при обеих раскладках | ≥ 97% |
| Время `LayoutScorer.score` p99 | ≤ 50 мкс |
| Размер моделей суммарно | ≤ 1 МБ |
| Время загрузки моделей | ≤ 5 мс |

Ложные срабатывания важнее полноты: лишняя коррекция разрушает текст, пропуск —
лишь неудобство (есть ручной хоткей). При конфликте целей порог сдвигается в сторону
меньшего FP.

## 9. Риски

| Риск | Митигация |
|---|---|
| Идентификаторы кода, аббревиатуры, пароли в не-secure полях выглядят «правдоподобно» в другой раскладке | консервативный порог для 4–5 букв; ползунок чувствительности; фильтры camelCase/ALLCAPS/цифр; правило «Не исправлять» в `PersonalLexicon`; per-app исключения уже есть |
| Короткие слова (`ns`→ты с margin 0.2) | `ShortWordTable` + подтверждение контекстом, как сейчас |
| Модель ошибается в выборе ru/uk (~3%) | учитывать активную кириллическую раскладку пользователя как приоритет, если обе установлены; `PersonalLexicon` |
| Лицензии корпусов | в модель попадают только агрегированные частоты n-грамм, но лицензии всё равно проверить и указать в README |
| Регрессия по сравнению со словарём на каких-то словах | флаг `detectionEngine` на время Фаз 2–4; eval-сравнение обеих систем |
| Рассинхрон `build-app.sh` ↔ `ModelLoader` при поиске ресурсов | перенести логику один-в-один; тест в `InputPipelineTestRunner` на отсутствие модели |

## 10. Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | n = 3 или 4 | **n = 3** сначала; 4-граммы с backoff — только если eval после Фазы 2 покажет пробелы |
| 2 | Тренер на Swift или Python | **Swift**, таргет `ModelTrainer`: общий с приложением код нормализации/хеша/формата исключает расхождения; release-сборка быстрая; один стек |
| 3 | Хранение выученных слов | **Открытым текстом**, отдельная вкладка «Слова» с полным CRUD (§4.5) |
| 4 | Настройка чувствительности | **Да**, ползунок из 5 положений; значение по умолчанию и шаги находятся перебором порогов на eval-наборе (§4.6), а не выставляются вручную |
| — | Конкретные пороги | Не фиксируются в плане; определяются бенчмарками Фазы 2 и уточняются по логам в Фазе 4 |
